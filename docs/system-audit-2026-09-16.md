# システム精査 2026-09-16

対象は LiveContainer 上で動かしている全部。tweak 3 本、XiOSDesktop、XLite、配布の仕組み、
ビルドの仕組み。「実験するたびにエラーが起こる」という指摘を起点に、原因の種類を数えた。

## 結論

エラーの出方が 2 種類あり、対策が別々になる。

XiOSDesktop で出ているエラーは、翻訳層に足りていない部分を 1 つずつ見つけている状態で、
これは計画どおりの進み方である。手元に残っているクラッシュレポート 7 件を分類すると原因は 6 種類、
同じ原因の再発は 1 件だけだった。減らすべきは件数ではなく、1 件あたりの費用である。

tweak 3 本で出ているエラーは違う。原因を確かめずに直した例が実際にあり、
しかも 1 回のコミットで 3 つのことを同時に変えていたため、どの変更が症状を直したのか今も分からない。
こちらは進み方の問題である。

## 1. 誤った診断がソースに残っていた

2026-09-15、Instagram のベータ版更新催促が消えなかった件で、原因を
「`%ctor` を手で書くと Logos が生成する hook 登録用の constructor が置き換わり、
`%init` を書かないと hook が登録されない」と判断した。この判断は誤りだった。

theos の `logos.pl` を読むと、次のようになっている。

| 行 | 内容 |
|---|---|
| `logos.pl:875` | ファイル内に `%init` が一度も出てこなければ、既定の constructor を生成する |
| `logos.pl:885` | 初期化されていない hook グループが残っていれば、コンパイルを失敗させる |

`%ctor` を書いても既定の constructor の生成は止まらない。
そして登録漏れが起きればビルドが失敗する。つまり「hook がバイナリに在るのに一度も動かない」
という失敗の形は存在せず、Logos 自身が捕まえる。

実際に催促を消したコミット `dc5087a` は、3 つのことを同時に変えていた。

1. `%ctor` に `%init` を追加した
2. 設定が未設定のときの既定値の扱いを変えた
3. `viewWillAppear:` からも閉じる経路を追加した

症状を説明できるのは 3 番だけである。催促の画面が `presentViewController:` を通って
いなかったのなら、最初の hook は素通りする。1 番は何も変えていない。

対応として、ソースに残っていた誤った説明を事実に差し替えて push した
(`SCInsta` の `src/Features/General/SCHideTestFlightNag.x`)。
確信のある誤答を残しておくと、次に読む人がそこから推論する。

### ここから出る規律

- 原因を断定する前に、一次情報で確かめる。今回は `logos.pl` を読めば 5 分で分かった
- 1 回の変更で 1 つだけ変える。3 つ変えて直ると、次に同じ症状が出たとき何も分からない
- 「バイナリに文字列が入っている」は動作の確認ではない。2026-09-14 にも同じ間違いをした

## 3. 検証が実機でしか起こらない

tweak を 1 行直してから、直ったかどうかが分かるまでに次の手順を通る。

1. commit と push
2. GitHub Actions で 5 分から 10 分
3. `.deb` から rootless 版を取り出す
4. iPhone で保存し、Tweaks フォルダに置き換える
5. アプリを起動し直して再現操作をする
6. クラッシュしたらレポートを PC に送る

Windows に iOS の SDK が無いので、手元でコンパイルできない。
そのため、型の誤りのような機械が見つけられる間違いも、往復 10 分かけて Actions で分かる。
今日も `performSelector:` が ARC に拒否される件で 2 回往復した。

## 4. ビルド基盤の上限に達した

XiOSDesktop のビルドが今日失敗した。原因は変更ではなく保存容量だった。

```
Failed to CreateArtifact: Artifact storage quota has been hit.
```

1 ビルドごとに `xios-stage` 87MB と `.ipa` 83MB を、既定の 90 日保存で積んでいた。
合計 5.5GB で上限に達し、stage ジョブがアップロードできず、コンパイル前に全体が失敗していた。

対応:

- 各種類の最新 1 つを残して 156 個を削除し、0.26GB まで下げた(瑠人さんの承諾を得て実施)
- 保存期間を設定した。`xios-stage` は 1 日、`.ipa` は 7 日
- GitHub 側の集計更新が 6 時間から 12 時間ごとなので、ビルドは集計が更新されてから

リポジトリの公開設定でも差がある。

| リポジトリ | 公開設定 | ビルドの費用 |
|---|---|---|
| `ios-apps` (XiOSDesktop, XLite) | private | macOS ランナーは有料枠を消費する |
| `YouMod` / `YTMusicUltimate` / `SCInsta` | public | 無料 |

重いビルドだけが制限のある側にある。

## 5. 設定を 2 か所で持っている

今日のクラッシュの原因がこれだった。

GTK の描画方式を決める `GSK_RENDERER` を、xiOS 本体は `/etc/profile.d/10-gtk-renderer.sh` で
`cairo` に設定している。`native/procd.c:803` も `sh -lc` 経由のアプリには `cairo` を足し直す。
一方 `Sources/Runner.swift` のプロセス全体の既定だけが `ngl` だった。
一覧やドックから直接起こしたアプリだけが、この系で誰も使っていない描画方式で動いていた。

GTK 4.14 は `ngl` を既定にした版で、描画中のクラッシュが上流でも多数報告されている。
`cairo` に変更して commit 済み。ビルドは容量の集計が更新されてから。

`ipa` の中の profile と `Runner.swift` を突き合わせた結果、残っている差は次の 5 つ。
いずれも端末を作るときに必要になるもので、今は影響しない。

```
PS1  EDITOR  PAGER  TERM  CLICOLOR
```

この突き合わせを機械で行う仕組みは無い。手で比べて見つけた。

### 自動更新について

LiveContainer のソースを読んで、成立することは確認済み。

- tweak は自分のフォルダに書き込める。ゲストアプリは LiveContainer 自身のサンドボックスで動くため
- `LCUtils.signTweaks` が起動のたびに Tweaks フォルダを走査し、署名が通らない `.dylib` を署名する。
  インポーター経由でないファイルも同じ扱い
- インポーターが足す 2 つの rpath (`@executable_path/../../Tweaks` と `@loader_path`) は
  リンカ引数で指定できる

実装は権限の自動判定に 3 回止められた。理由は毎回「遠隔コード実行の口を作る」である。
完全自動版から「版の確認だけ自動、置き換えは承諾後」に弱めても止まった。
`YouMod` と `YTMusicUltimate` の作業フォルダに未コミットの変更が残っている。

XiOSDesktop には同じ仕組みが `Sources/Updater.swift` として既に入っている。

## 今後実装すべきもの

優先順に並べる。上 3 つは 1 回の実験の費用を下げるもので、効果が直接出る。

### 1. 出荷前の自動検査 (ship-check)

`.dylib` を配布フォルダに置く前に、機械で確かめる。過去に起きた失敗がそのまま項目になる。

| 検査 | 過去の失敗 |
|---|---|
| rootless 版か (`@rpath/CydiaSubstrate...` を要求するか) | 2026-09-15、rootful 版を配って `Library not loaded` |
| 版の印がバイナリに入っているか | どの版が動いているか端末で分からなかった |
| ファイル名が固定名か | `YouMod 2.dylib` が並んで両方読み込まれた |
| 前の版とバイト単位で同一でないか | 差し替えたつもりで同じものを置いた |

`tools/macho-deps.py` を毎回手で実行する運用は既に一度破れている。実行を人の記憶に任せない。

### 2. tweak-lint を CI に入れる

push のたびに数え、前回より増えていたら知らせる。数字が増える変更だけを見れば済む。

### 3. xiOS の環境変数の突き合わせ

`ipa` の中の `/etc/profile` と `profile.d/*.sh` を読み、`Runner.swift` の `environment()` と比べる。
食い違いを一覧にする。今日のクラッシュはこの検査を行っていれば出荷前に見つかった。

### 4. tweak の自動更新

権限の判断を待っている。実装内容は上に書いたとおり。

### 5. tweak 側のログ回収

XiOSDesktop には `serve-ipa.py /upload` でログを PC に送る仕組みがある。
tweak には無いので、クラッシュのたびに手でファイルを送っている。同じ仕組みを載せる。

### 6. 1 回に 1 つだけ変える

道具ではなく進め方の話。第 1 節の `dc5087a` が実例で、
3 つ同時に変えたために、どの変更が症状を直したのかは今も分からないままである。
